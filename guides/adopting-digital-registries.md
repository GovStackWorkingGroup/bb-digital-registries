# Adopting Digital Registries <a href="#guide-adopter-kit" id="guide-adopter-kit"></a>

This companion guide helps deployment authors prepare Registry metadata and concrete API contracts. The functionality files define the requirements; these steps show how to use the supplied examples.

| Artifact | Where it is served | Start from | Defined by |
|---|---|---|---|
| OpenAPI contract, one per API | A stable URL chosen by the deployment | The [example matching the selected capabilities](../resources/api-examples/README.md), using the unified [Registry API contract](../resources/api.yml) | [Consultation HTTP binding](../requirements/registry-services.md#consultation-http-binding), [Write binding](../requirements/registry-services.md#write-write), and [API composition](../requirements/registry-discovery.md#core-api-composition) |
| Registry metadata document | A stable document URI, served as `application/ld+json` | [Registry metadata example](../api/examples/registry-metadata.jsonld), validated by the [metadata document schema](../api/extensions/registry-metadata.schema.json) | [Registry metadata](../requirements/registry-discovery.md#core-registry-metadata) |
| API catalog linkset | `/.well-known/api-catalog` at the API origin, served as `application/linkset+json` | [API catalog example](../api/examples/api-catalog.linkset.json) and the `/.well-known/api-catalog` path of the [canonical Registry OpenAPI](../resources/api.yml) | [Discovery publication](../requirements/registry-discovery.md#core-discovery-publication) |
| Health endpoint | `/health` relative to the OpenAPI server URL, including any routing prefix | The `/health` path of the [canonical Registry OpenAPI](../resources/api.yml) | GovStack API Design Guide, unversioned health endpoint |

## Producing the artifacts <a href="#guide-producing-the-artifacts" id="guide-producing-the-artifacts"></a>

1. **Contract.** Choose the examples matching the operations and features you need. The household and birth-registration examples show concrete logical Collections; the business example selects additional read behaviour; the Write examples show direct and approval-based changes. Replace the literal `collectionId` and domain schemas while preserving the `/v1/collections/{collectionId}` hierarchy and shared `$ref` links for parameters, headers, responses, and security schemes. Every selected Collection-scoped Consultation operation keeps its `x-govstack-digital-registries` declaration, with `registry` set to your Registry Identifier and `collection` equal to its path value. Every selected primary Write operation keeps its Write declaration and publishes its input mapping, grant, and target. Add only the capabilities and selectable `features` the operation implements and can verify; an omitted or empty array declares none. A `purpose-bound` operation also requires its trusted `purpose` declaration. An Update or Transition companion read points to the shared `retrieveRecord` operation for the exact same Registry, Collection, and view and uses its strong validator; it does not add a competing `GET`. Derive that response body and tag from one current authoritative guard evaluation, and invalidate the tag for every field or source condition that can change the mutation's validation, mapping, or committed effect. Do not designate the view when disclosure policy forbids revealing the opaque tag or its change cadence. Caller capability discovery uses its separate bounded response schema. Put Collection-scoped Consultation and Write operations under `collections`; put cross-Collection Change Request and Operation-status entries under optional root `operations`. Give recognised Consultation entries a `view`, keep read-only annotations off Write entries, and include `write.companionRead` for Update and Transition. Existing recognised read entries can omit `family`; new Write entries declare `family: write`. Align each selection with its inputs, response headers, schemas, permissions, and guarantees.
2. **Metadata document.** Describe one Registry (`@id`, `title`, `description`, `authority`, `specification`, `dataService`) and one data service per API (`serviceType`, `endpointURL`, `endpointDescription` pointing at the contract). Validate the document against the metadata document schema with any JSON Schema validator. The document is plain JSON; RDF tooling is not needed unless a catalogue integrator wants it, in which case the [metadata vocabulary appendix](../requirements/registry-discovery.md#vocabulary-metadata-vocabulary-informative) explains the mapping.
3. **Linkset.** Serve the API catalog with one `service-desc` link per contract and one `service-meta` link to the metadata document.
4. **Health.** Expose `/health` relative to the OpenAPI server URL, for example `/registry/health` when that URL includes `/registry`.

## Checking the artifacts <a href="#guide-checking-the-artifacts" id="guide-checking-the-artifacts"></a>

The repository's artifact validator, `tools/validate_consultation.py`, checks the example contracts, schemas, fixtures, metadata document, and linkset shipped with this specification; the [validation commands](../resources/testing.md#artifact-validation) show how to check the shipped artifacts. The API directory's contributor instructions also document the GovStack API Design Guide linter. Adopters run the same linter against their own contract and validate their metadata document against the schema. [Testing](../resources/testing.md) covers verification of a deployed implementation.

## What is not needed <a href="#guide-what-is-not-needed" id="guide-what-is-not-needed"></a>

- A catalogue API or Provisioning API: static documents satisfy discovery.
- All read or Write operations: the draft variation point selects at least one, as described in [Conformance](../introduction/scope.md#conformance-draft-conformance-model). Direct writes and approval-based writes remain independently selectable.
- Conditional requests, caller-selected fields, exhaustive traversal, or source snapshots unless the operation declares the corresponding feature.
- Revision history, recorded-time or effective-time selection, caller capability discovery, or purpose binding unless the corresponding capability or feature is selected.
- Revision, lifecycle, or provenance metadata, unless a selected profile requires it.

## Adopting Write <a href="#guide-adopting-write" id="guide-adopting-write"></a>

Select the direct operations or approval-based route the source and policy support, using the unified [Registry API contract](../resources/api.yml) and [Write binding](../requirements/registry-services.md#write-write). Publish the concrete input schemas, named transitions, grants, trusted purpose rules where selected, companion guard coverage, idempotency replay contract, and commit boundaries. Approval-only deployments publish request and review operations without granting direct Write access. Returned acknowledgements do not imply permission to retrieve every resulting Record or guarantee that a permitted projection is immediately current. A matching tag is expected only when a later companion Retrieve has reached companion currency and observes that exact committed state, with no intervening mutation-relevant change, under the same effective authorisation, disclosure, purpose, and field-selection context. This is not a promise of eventual equality on a future Retrieve.

The [non-normative Write examples](../resources/api-examples/README.md) show one possible set of domain bindings, not a required data model. Document the institution's chosen model version, mappings, extensions, and licence attribution. Validate Write artifacts with `uv run python tools/validate_write.py`; use [Write verification](../resources/write-testing.md) for implementation scenarios.
